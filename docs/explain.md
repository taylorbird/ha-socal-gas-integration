# Why the Usage API Rewrite Was Needed

**The original integration** was built around SoCal Gas's Green Button API — a standardized energy data export format. You'd authenticate via browser automation (because socalgas.com requires JavaScript), capture an access token, then hit a ZIP download endpoint that returned XML files containing your hourly gas usage for any date range you requested. The coordinator would chunk your desired lookback period into 30-day windows, download each chunk as a ZIP, extract and parse the XML, and feed everything into Home Assistant's long-term statistics. It worked well enough for accounts that had Green Button enabled.

**The problem** is that SoCal Gas quietly broke (or deprecated) the Green Button backend. The ZIP download endpoint at `/greenbuttonservices/api/greenbutton/zipfile` started returning HTTP 500 with an empty body for every parameter combination. The alternative path through `/connectorsso/api/usage/greenbutton` returns a 701 error code: "The Analyze Usage tool is not available for this account." This isn't an auth issue or a parameter mistake — the endpoints are simply dead server-side. No amount of tweaking request formats fixes it.

**What we discovered:** We opened up browser DevTools on the actual SoCal Gas "Analyze Usage" page and captured the network traffic to see what endpoints their own frontend uses. Turns out they have a completely separate set of internal APIs: a monthly endpoint that returns your billing cycles (about 12 months of summary data including dates, costs, and CCF values), and an hourly endpoint that returns granular per-hour usage for any single billing cycle. These endpoints use slightly different field names and types than the old Green Button API, but they're actively maintained because they power the website.

**The rewrite** fundamentally changes how we fetch data. Instead of "give me a date range and I'll download everything in 30-day chunks," the new approach is "tell me your billing cycles, then I'll fetch hourly data for each one." On first run, we grab all billing cycles that have actual charges, then fetch hourly data for each. On subsequent polls, we only fetch the current open cycle and the most recent completed one — just enough to stay current without re-downloading everything. The sensor and statistics layers are completely untouched.

**Why this is better:** Billing cycles are the natural unit of data organization for a utility — that's how SoCal Gas structures it internally. We're also calling the same endpoints the website relies on, which means if they work for socalgas.com users, they'll work for us. The old Green Button API was always a secondary export feature that could be quietly killed (and was). The usage API is load-bearing infrastructure for their customer portal.
